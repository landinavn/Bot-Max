# Security 1.1 — безопасная миграция legacy media

Статус: подготовка и синтетические тесты. Никаких действий с рабочей БД/бакетом не выполнено. База кода: `57744a0b600a9736cbaf1d00a2ccb6660869c903`. Реализация — [private_media_migration.py](../private_media_migration.py).

## Принципы

1. Новые объекты записываются в отдельный private bucket. Старый bucket, его global policy и ACL не меняются.
2. Старый публичный URL остаётся работоспособным для существующих заказов. Наличие новой private копии **не закрывает старый URL**.
3. Не угадывать владельца по key, изображению, share token или пользователю, приславшему URL. Нужна связь с сохранённым заказом/проектом.
4. Не менять ссылки активных заданий и не отзывать доступ до проверки всех provider jobs, очередей, ручных блокировок и RAM FSM.
5. Не очищать paid POST submitting markers, не создавать новые генерации «для проверки», не восстанавливать старую бизнес-БД при rollback кода.

## Dry-run inventory

`inventory` читает указанный SQLite через URI `mode=ro` в read transaction. Никаких S3 calls, генераций, ACL writes или изменения SQLite. Сканируются строки и JSON в обычных rowid-таблицах; legacy URL распознаётся только под точной настроенной HTTPS base с каноническим key. Signed/query URLs, credentials, traversal, двусмысленное URL encoding и внешние домены не считаются безопасной целью миграции. WITHOUT ROWID и неподдержанные структуры не переписываются.

План содержит table/column/rowid/JSON path, object key, SHA исходной строки и вывод о владельце; **не содержит raw URL**. План всё равно чувствителен: key и owner/order ID относятся к пользовательским материалам. `--plan` создаёт новый файл эксклюзивно с 0600; stdout печатает только агрегированные количества. Не публиковать план в Git/PR/чат, хранить вне web root. CLI никогда не копирует и не переключает production автоматически.

Пример для будущей проверки **отдельной тестовой копии**, не команда для запуска сейчас на production:

```bash
python private_media_migration.py --help
python private_media_migration.py --database /secure/test-copy.sqlite3 --plan /secure/new-private-media-plan.json
```

Используются существующие настройки legacy base/bucket, но реальные secrets не выводятся. Перед выполнением сверить CLI `--help` именно проверенного SHA. Не подставлять путь рабочего файла вместо тестовой копии без отдельного решения владельца.

## Установление владельца

* Строка заказа: проверенный `user_id` и `order_id` из БД.
* `photo_results`: JOIN `photo_orders` по order_id.
* `cartoon_assets`: JOIN `cartoon_projects` по project_id.
* Нет достоверной связи, несколько возможных владельцев, произвольная исходная ссылка, shared_images: `ownership-unverified`, автоматическое копирование запрещено.

Даже наличие `user_id` не доказывает право на произвольную вставленную ссылку. Автоматический whitelist ограничен сгенерированными выходными полями с ожидаемым prefix: `photo_results.image_url/vision-boards`, `cartoon_orders.result_url/videos`, `musical_orders.result_url/videos`, `audio_orders.preview_url/audio-previews`, `cartoon_assets.public_url/studio|multstudio`. Доказательство этих полей не распространяется на fsm_data, исходные фото и публикационные share tokens.

## Копирование

`copy_one` — вызываемый отдельно API, не CLI массовой миграции:

1. Повторно прочитать исходную строку, owner/order/proof, сравнить locator и SHA с планом.
2. Авторизованный legacy SDK HEAD/GET конкретного key. Никакого anonymous HEAD и никаких bucket list/ACL changes.
3. Ограничить размер 200 MiB, проверить ContentLength, прочитать байты.
4. Записать новую private копию через `PrivateMedia.put`; operation ID зависит от legacy bucket/key и owner/order. Повторное выполнение на том же source идемпотентно; другой SHA не затирает результат.
5. Сохранить private ref в защищённом журнале оператора. Исходный DB URL, source object и ACL остаются прежними.

Если owner неизвестен, исходник изменился/недоступен, MIME не поддержан или private storage недоступен — остановить этот объект. Не делать fallback в публичный bucket. Unknown PUT не повторять без SDK HEAD и проверки сохранённой операции. Чужой объект нельзя привязать к заказу.

## Переключение: намеренно ограниченный первый этап

Реализован только `cutover_completed_photo` для **доставленного результата завершённой фотосессии**. Для других сценариев переключение блокируется до отдельной проверки всех читателей/фоновых задач. Это ограничение предотвращает массовую несовместимую замену URL в неизвестных snapshot.

Обязательны все условия:

* Сервис остановлен штатно и новые события не обрабатываются; RAM FSM сохранены либо выяснено, какие сессии требуется завершить до окна.
* Оператор отдельно проверил provider task IDs **только GET**, отсутствие активных/неизвестных запросов и готовность продолжения по старому ID.
* `activity` не видит незавершённых/непонятных заказов и живых leases. Это консервативный сигнал БД, а не доказательство отсутствия внешних jobs; ручная проверка обязательна.
* Результат photo_results уже delivered; приватная копия существует и HEAD/SHA/owner/order подтверждены.
* Operation ID копии соответствует конкретному исходному legacy key.
* Compare-and-swap исходного URL всё ещё совпадает с SHA плана.

Изменяется **только `photo_results.image_url`**; не баланс, цена, оплата, счётчик генераций, state, статус заказа или схема бизнес-БД. Повторный cutover того же private ref возвращает `already-private`. Отказ на любой проверке оставляет source неизменённым. Сначала прогнать на синтетической/разрешённой тестовой копии, затем получить отдельное согласование реального cutover.

## Активные jobs и legacy публикация

Проверять обе системы: поля БД и внешний provider. Сохранённый ID с manual/failed/unknown требует выяснить, был ли запрос принят и платен. Не удалять этот ID ради запуска нового. Наличие `submitting` без ID и RAM-only FSM — основание отложить изменение доступа. Не считать `queued` безопасным только потому, что provider_id пустой.

`shared_images` — отдельная история добровольной публикации. Скопировать исходник в private не означает, что прежний публичный share link отозван. Закрытие/удаление legacy объекта, очистка CDN/cache, отзыв share token и последствия для старых заказов должны быть отдельным согласованным этапом после инвентаризации ссылок и задач. В этом коде этих destructive операций нет.

## Rollback

До новых private записей можно оставить feature flag off. После появления private ref:

* Отключить **новые записи/обработку**, но сохранить reader-capable Security 1.1 код, registry, private credentials и bucket.
* Не откатывать слепо на Security 1.0/fallback: их readers не понимают `private-media:v1:`. Нужен отдельно проверенный reader backport либо остановка затронутой обработки.
* Не делать private bucket/object public ради старого reader.
* Не восстанавливать старую business DB: потеряются новые оплаты/заказы. Registry и business DB должны оставаться согласованными.
* Если reader нельзя безопасно поддержать, остановить соответствующие сценарии, сохранить материалы и IDs, устранить проблему отдельно.

Срок хранения source/copy/plan/backup здесь не вводится. Последующее удаление требует самостоятельного проекта и решения владельца.
