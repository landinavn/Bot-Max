# Security 1.0 — TLS MAX и безопасное логирование

Дата: 27 ноября 2026. Ветка: `security/max-tls-safe-logging`.

## Границы и исходная версия

Точный base: **`48d4c5918013069483a2292c5e46e626798f24cb`**, актуальный main, полученный перед началом работы. Это та же версия, которую проверял privacy-аудит: различий между актуальным base и проверенным аудитом main нет.

Основание: [draft PR №263](https://github.com/landinavn/Bot-Max/pull/263), документ `docs/privacy-data-audit.md`, коммит `b6e2035b4657b5c0b568625f88056d782bd12bab`, особенно раздел 16.2. Сам документ аудита не копируется в эту ветку.

Изменения ограничены MAX TLS-клиентом, политикой журналирования, соответствующими тестами и этим отчётом. Не включены ветки web-авторизации, финансового ядра и frontend. Не изменялись цены, промо, начисления, списания, пользовательские маршруты, финансовые записи/доказательства, provider task IDs и правила восстановления. В webhook изменено только журналирование, без изменения валидации, подписей, ответов и транзакций.

Production/VPS, Small Talk, рабочая БД, системные CA/прокси/firewall/journald/Nginx не использовались и не менялись. Реальные платежи, генерации, рассылки и доставка клиентских материалов не выполнялись. Все HTTP-проверки — mocks или локальный HTTPS; данные синтетические.

## 1. История отключения TLS

`max_client.py` появился в коммите **`7273c4e6e9262e63de100305354c7fcc40ae29ce`**, `fix: share MAX client with SSL disabled for API and media uploads`, затем изменения вошли в [PR №25](https://github.com/landinavn/Bot-Max/pull/25). В нём прямо описаны `TCPConnector(ssl=False)` для API/polling/upload-хостов и полное журналирование ответов/traceback. Старые тесты закрепили это поведение.

**Техническая причина необходимости обхода в доступной истории не подтверждена.** Ни конкретная ошибка цепочки/hostname/срока, ни утверждённый дополнительный CA, ни сетевые особенности production этим PR/коммитом не доказаны. Нельзя задним числом объявлять это проблемой российского CA или прокси.

В исследованной установленной библиотеке maxapi есть собственный путь загрузки дополнительного bundled CA. Новый код его автоматически не выбирает: передаёт собственный явный connector с системным SSLContext. Сторонний CA не добавляется без отдельного согласования.

## 2. Новый сетевой контракт

`MaxAPIConnector` создаёт `ssl.create_default_context()` и передаёт полученный контекст в aiohttp. Для клиентского HTTPS это включает `CERT_REQUIRED`, проверку цепочки/сроков и hostname. Используются доверенные корни системной Python/OpenSSL-конфигурации; новый bundle, переменная переключения TLS или автоматическое доверие сертификату не добавлялись.

Дополнительно `connect()` отклоняет HTTP до открытия соединения: в том числе нельзя автоматически перейти с HTTPS на HTTP по redirect. Для MAX API и upload/download применяется один и тот же connector. Другие провайдеры не переведены на этот connector, их сетевые настройки сохранены.

- Нет `ssl=False`, `verify=False`, `CERT_NONE`, `check_hostname=False` или небезопасного fallback в прикладном сетевом коде этой ветки.
- Не добавлены retry платных AI-запросов. Существующие guards неизвестного результата POST, сохранённые task IDs и восстановления не менялись.
- SDK MAX сохраняет свои прежние настройки retry. Это доставка/запросы MAX, а не новые генерации AI; тесты TLS отдельно исключают принятие HTTP-запроса при плохом сертификате.
- `create_max_bot()` используется основным процессом и дополнительными клиентами `upload_photo` / `generate_poster`. Установка API URL перенесена внутрь `try/finally`: сессия закрывается и при ошибке setup. Внешним connector владеет контекст приложения.
- Нормальные, аварийные и отменённые операции закрывают сессии/connector. Ошибка сертификата не лечится повторным подключением без проверки.

Фактическое доверие CA на VPS не проверено. Если текущая цепочка MAX не доверена системой, операция должна завершиться ошибкой. Это повод отдельно исследовать цепочку и согласовать доверие, а не возвращать обход проверки.

## 3. Политика журналирования

Добавлен `safe_logging.py` с двумя защитными уровнями.

### Прикладной facade

Все runtime-модули с собственным logger используют `get_logger(__name__)`. Facade не форматирует и не передаёт legacy message, args, `extra`, исключение, response, raw body или traceback в logging. Вместо них создаётся диагностическая запись из разрешённых полей: источник модуля, функция/строка кода, event code и случайная корреляция. У ошибки сохраняется ограниченная классификация, без `str(exc)`, `repr(exc)` и имён произвольных классов.

Для важных API-путей используется явный `.event(...)`: сохраняются ограниченные HTTP status, product, stage/error code. Старые сообщения «исходный текст», «промпт», «результат URL» и переданные им значения не попадают в журнал даже при существующем legacy вызове: facade обрабатывает его как недоверенный контент. Это общий fail-closed механизм, а не регулярная замена известных ключей или попытка угадать все имена/телефоны.

### Граница stdlib logging / SDK

Устанавливается LogRecordFactory: только внутренний SafeEvent может передать разрешённый payload. Произвольные записи HTTPX/httpcore/aiohttp/MAX SDK/OpenAI/boto и других logger превращаются в `external_diagnostic` с безопасной группой источника и уровнем. Исходные message/args/exception/stack не форматируются и не передаются предыдущей factory.

Карта полей LogRecord отбрасывает неизвестные `extra`, которые stdlib добавляет **после** factory: туда нельзя протащить Authorization/headers/payload. У принадлежащих приложению handlers дополнительно устанавливается фильтр. `exc_info`, `exc_text`, `stack_info` очищаются; имя async task не выводится как пользовательская метка.

Политика устанавливается при создании прикладных logger, при конфигурации основного процесса и перед созданием любого MAX-клиента. Будущие handlers получают уже безопасное сообщение. Смена factory/добавление стороннего прямого вывода в stdout отдельной библиотекой требуют нового review; это не защита от намеренного исполнения произвольного Python-кода.

### Разрешённые поля

| Поле | Ограничение |
|---|---|
| `event` | Закрытый набор кодов операции; неизвестное значение становится `diagnostic` |
| `source`, `stage`, `line` | Имена модулей/функций и строка исполняемого кода; не данные из события клиента |
| `product` | Закрытый набор продуктов, без индивидуального названия/описания заказа |
| `http_status` | Только int 100–599; строки, bool и объекты отклоняются |
| `duration_ms` | Ограниченный неотрицательный int, без произвольных пользовательских полей |
| `error_code` | Ограниченная классификация ошибки; не ответ API и не текст исключения |
| `correlation` | Новое случайное значение, не MAX ID/order ID/task ID и не их hash |

В пользовательском handler корреляция задаётся в `UserActivityMiddleware` на время вызова handler и возвращается назад в `finally`. Контекст не меняет событие, маршрутизацию или результат. В фоновых legacy-логах без такого scope создаётся отдельная случайная метка записи: она не обещает связать весь job; для расследования остаются сохранённые защищённые задания/платёжные инциденты.

Пример безопасной структуры (метки условные, не клиентские):

```json
{"event":"api_error","source":"image_service","product":"image","http_status":400,"stage":"_raise_api_error","line":1,"correlation":"0123456789abcdef"}
```

Идентификаторы клиентов/счетов/провайдера из журналов убраны, но **не удалены из БД** и не заменены в механизмах восстановления. Hash MAX ID не используется как «анонимизация».

## 5. Тесты и окружение

Проверенная установка: Python 3.12.14, maxapi **1.2.3**, aiohttp **3.13.5**, pytest **9.1.1**, OpenAI SDK **2.54.0**, HTTPX **0.28.1**, aioresponses **0.7.9**, respx **0.23.1**. Для ограничения зависания сравнительных прогонов добавлен test-only `pytest-timeout>=2.3,<3`; использована версия **2.4.0**. Production-версии зависимостей неизвестны; здесь они не обновлялись. OpenSSL CLI используется только для выпуска локальных синтетических сертификатов.

### Новые проверки

- Реальный handshake на локальном aiohttp HTTPS-сервере: доверенный тестовый CA, неизвестный CA, просроченный leaf, несовпадение hostname. Только тест подставляет свой CA-контекст; в production такого bundle нет.
- Реальный SDK transport: updates с message/callback, callback answer, send/edit, image/file/audio/video upload, отправка вложений как готовых результатов, download bytes, закрытие сессий/connector.
- API, прямой upload и download отклоняются при каждом плохом сертификате; HTTP не открывает соединение. Ошибки setup/cancel также закрывают ресурсы.
- Дополнительные клиенты image_service проверяются существующими mocks с новыми строгими TLS-assertions и сохранённой проверкой закрытия/результата.
- Синтетические имена взрослого/ребёнка, персональный текст, email/телефон, токен, private/signed URL, вложенный JSON, provider error body, исключение и цепочка traceback не появляются ни в выводе, ни в аргументах/exception-полях LogRecord.
- Отдельно проверены SDK logger, headers/extra после factory, объект с запрещёнными `__str__/__repr__`, восстановительный preflight и неизменное число платных POST при ошибках.
- Проверка AST запрещает прикладные raw `logging.getLogger` вне политики и динамические operation literals в явных событиях.

### Совместимость прежних тестов

Существующие тестовые функции и параметризация сохранены. Там, где старый контракт требовал `CERT_NONE`, полного ответа/текста/traceback, assertions заменены на `CERT_REQUIRED` + hostname и структурированное событие + отсутствие контента. Проверки request payload, получателя, return value, сохранённого результата, SQL-состояний, task ID, количества POST и повторов не убраны. Ни одного skip/xfail для сокрытия security-регрессии не добавлено.

Повторная адресная проверка одной параметризованной функции прошла (3 passed); runtime-код после полного прогона не менялся.

Итоговые JUnit/log/comparison-артефакты сохранены вне Git. Полные логи тестов не коммитятся: в них могут быть синтетические секретные маркеры, необходимые для negative assertions. SHA-256 freeze тестового окружения: `dd22157377078c668ddb0aca115b2e2695a0a57b050ca3a28a6455a89528afad`. SHA-256 общего изолирующего runner: `39562423aa613dfeded9595bc1e477ef7db19f68bb311577b5b61ba0ae83c409`.


Сравнение выполняется на одном установленном наборе зависимостей, с одинаковым ограничением внешней сети и разрешением только loopback, с `MAX_BOT_TOKEN` синтетического тестового окружения. Рабочая БД не используется. Все testcase сравниваются по точному ID, отдельно от числа passed/failed.

Команды pytest для обоих checkout одинаковы:

```text
python <isolated-network-test-runner> -q --timeout=90 --timeout-method=signal -o faulthandler_timeout=60 --tb=short --junitxml=<result.xml>
```

Внешний runner блокирует Python socket connect/connect_ex к любым адресам, кроме `127.0.0.1`/`::1`; API/объектное хранилище тестируются mocks. Одинаково в обоих checkout runner заменяет служебный self-pipe asyncio на неблокирующий `os.pipe`, чтобы изоляция socket не мешала механизму пробуждения event loop. Эта sandbox-обвязка находится вне runtime-кода/PR и не применяется к боту. На обычном тестовом Linux без такого ограничения self-pipe можно использовать стандартный pytest в среде с запрещённым внешним egress. Первые диагностические прогоны с полностью запрещённой сетью/без разрешения bind localhost нельзя считать сопоставимым результатом: они блокировали собственные aiohttp TestClient/HTTPS-серверы. Они не выдаются за результат исправления.

## 6. Оставшиеся риски и ограничения

1. **Нет реального smoke MAX:** системный trust store, цепочки upload-хостов, прокси и версии библиотек VPS ещё не проверены. Безопасный отказ возможен и предпочтительнее обхода проверки.
2. Логирование сознательно теряет детали произвольных SDK-ответов/traceback. Для диагностики есть source/stage/line/status/correlation и прежние защищённые записи в БД; полный response не предлагается временно включать даже при ошибке.
3. Глобальная factory действует в Python-процессе бота. Будущий код не должен заменять её, добавлять собственное форматирование raw payload, прямой stdout/логирование до установки политики или собственные handlers с обходом границы. Это проверяется при интеграции, а не обещается для произвольных библиотек.
4. Предыдущие журналы, админские сообщения/выгрузки, backup и серверные access/error logs не очищены. Изменение не удаляет уже существующие копии и не определяет юридические сроки.
5. Публичные URL в бакете, согласия, удаление ПД и условия поставщиков остаются отдельными находками privacy-аудита. Закрытие утечки URL в журнал не делает сам URL приватным.
6. Полные тексты ошибок могут оставаться в прежних исключениях/защищённых заданиях для текущего восстановления и в отдельных клиентских ответах; данная задача меняет их попадание в журналы, а не весь продуктовый error/UI-контракт.
7. Hash/случайная корреляция не объявляются анонимизацией пользовательских записей. Метки журнала не строятся из MAX/order/provider IDs.

## 9. Старые journald/Nginx logs и backup — отдельный план

Этот план не предоставляет разрешение читать или удалять реальные журналы сейчас.

1. Составить перечень journald units/namespaces, отдельных Nginx access/error logs, агрегаторов, архивов, ротаций, snapshot и backup. Проверить владельца, права, группы/ACL и круг доступа на уровне метаданных, не публикуя содержимое.
2. Уточнить текущие rotation/retention и возможные требования сохранения доказательств. Решение о сроках/ограничениях/удалении утверждает оператор с ответственным за документы; не назначать вымышленный срок.
3. Ограничить доступ к прежним журналам и их копиям в рамках согласованной модели. Проверить скачанные выгрузки/копии и внешних сборщиков. Не редактировать и не удалять финансовую БД или доказательства платежа под видом очистки журналов.
4. На VPS с другими проектами **не менять глобальный journald.conf и не выполнять общий vacuum**. Общий journal может содержать несколько сервисов; выборочная очистка одного приложения не должна уничтожить чужие записи. При необходимости отдельно спроектировать выделенный поток/namespace для дальнейших логов.
5. Для Nginx использовать только согласованный app-specific log/rotation policy; не трогать основной сайт, webhook, Small Talk и общие журналы остальных проектов. Права/формат/сроки реальной конфигурации сейчас неизвестны.
6. Утвердить безопасное уничтожение/ограничение архивов и backup с протоколом выполнения, исключениями обязательного хранения и проверкой восстановления. Не считать удаление активного файла доказательством исчезновения всех копий.
7. Результат оформить отдельным документом/заданием с точным охватом, ответственными и подтверждением. Здесь нет команд массового удаления и ничего не применено.

## 10. Совместимость с будущим MAX-linking

Ветка linking не влита и не использована. Для интеграции:

- Переиспользовать `create_max_bot()` и системный проверяющий connector; не создавать альтернативный клиент с `ssl=False` или автоматическим доверием bundle.
- Использовать `get_logger`/разрешённые события; не логировать linking code, nonce, credential, session token, redirect URL/query, email, MAX ID или headers. Не выводить их hash как «обезличенный» substitute.
- Разделять внутреннее сохранение доказательств связывания в защищённой БД и журнал приложения. Корреляция — случайная метка операции.
- Новые exception middleware/SDK/handlers не должны заменять factory или восстанавливать сырой traceback. Повторить privacy-регрессии после интеграции и проверить новые transports на локальном HTTPS.
- Транзакции аккаунтов/прав, срок linking-кода и UI не определяются этим security-патчем.
