# Единые аккаунты — этап 1.1

Этот слой пока **не подключён** к MAX-боту, его `bot.py`, `database.init_db()`,
платежам, бесплатным генерациям или продуктовым заказам. Новые модули не импортируют
`Config`, `database`, `maxapi` и не читают `.env`. Импорт и создание объекта
репозитория не открывают БД. Production-копии и ключи для разработки не нужны.

## Данные и источник истины

- `accounts`: `id TEXT PRIMARY KEY`, `created_at`, `updated_at`.
- `account_identities`: `id TEXT PRIMARY KEY`, `account_id`, `provider`,
  `provider_subject`, `verified_at`, `created_at`.
- `account_schema_migrations`: версия, имя, SHA256 определений и дата применения.

Все даты — UTC; идентификаторы записей — UUIDv4 в каноническом строковом виде.
UUID не содержит MAX ID. В SQLite используется TEXT; при будущем переходе
PostgreSQL его можно отобразить на native UUID, не меняя внешние значения.
Статус аккаунта пока не добавлен: блокировка/удаление требуют отдельной политики,
которой нет в этом этапе.

Единственный источник связи `(provider, provider_subject) → account_id` —
`account_identities`, защищённая уникальным индексом. Отдельная
`legacy_account_links` не нужна: MAX subject — строковая каноническая запись
существующего `users.user_id`. Два источника соответствий создали бы риск расхождений.
FK `account_identities.account_id → accounts.id` включается на каждом соединении;
удаление аккаунта с идентичностями запрещено (`RESTRICT`). Есть индекс поиска по
владельцу и частичный уникальный индекс: не больше одной MAX-идентичности у аккаунта.
Несколько разных email у одного аккаунта допустимы. Provider не ограничен ENUM,
чтобы позднее добавить другие каналы; правила владения ими всё равно обязательны.

`users`, балансы, платежи и все продуктовые таблицы остаются прежними.
Веб-аккаунт без MAX создаёт только запись в `accounts`, а с подтверждённым email —
ещё одну идентичность. Фиктивного `users.user_id` нет.

## Контракт доверия

`AccountRepository` — привилегированный **внутренний** компонент, не система
авторизации и не публичный API. Все операции требуют явного пути к существующей БД.
Файл не создаётся скрыто; используется SQLite URI `mode=rw` или `mode=ro`.

- `create_account()` создаёт независимый аккаунт без идентичностей.
- `get_account(id)`, `get_account_by_identity(provider, subject)` возвращают аккаунт
  или `None`; поиск не является подтверждением личности или входом в аккаунт.
- `list_account_identities(id)` возвращает идентичности (пустой список при отсутствии).
- `get_or_create_max_account(max_user_id)` вызывается только доверенным адаптером,
  получившим ID из аутентифицированного события MAX. Это **не** способ войти с
  произвольным введённым MAX ID. Legacy-пользователь обязан уже существовать;
  иначе `LegacyMaxUserNotFound`, без создания аккаунта или пользователя.
  При отсутствии/несовместимости `users` возвращается `LegacySchemaError`.
- `create_account_with_verified_email(email, verification=VerifiedIdentity(...))`
  допустим только после реального подтверждения владения email доверенным сервисом.
  Обычная строка/словарь не служит подтверждением. Объект должен содержать именно
  этот нормализованный адрес, provider `email` и фактическое время подтверждения.
  Занятый адрес даёт `IdentityConflict`; другой аккаунт не объединяется и не входит.
- `_add_verified_identity(...)` — внутренняя низкоуровневая операция. Вызывающий
  сервис должен **отдельно** проверить права на целевой аккаунт и владение новой
  идентичностью. Нельзя превращать её в endpoint «прикрепить произвольный MAX/email».

`VerifiedIdentity` — типизированное утверждение доверенного кода. Его можно
сконструировать в Python: это **не криптографическое доказательство**, не проверка
почты и не защита от недоверенного кода внутри процесса. Нельзя десериализовать
его из браузерного запроса. Фактические email-коды, авторизация и двухсторонняя
привязка будут отдельным следующим этапом. Данные идентичности не пишутся в логи;
subject скрыт из стандартного repr моделей.

## Осторожная нормализация

MAX ID: только Python `int` (не bool), от 1 до 2^63−1. MAX subject при общем поиске
— каноническая десятичная строка без ведущих нулей. UUID — канонический lowercase.

Email: поддерживается обычный ASCII addr-spec без display name, кавычек и
управляющих символов. Удаляются только наружные пробелы, домен приводится к
нижнему регистру. Локальная часть сохраняет регистр, точки и `+`-алиасы:
`Alice+one@EXAMPLE.TEST → Alice+one@example.test`. `a.b` и `ab`, `a+one` и `a+two`,
`Alice` и `alice` не объединяются. Это осторожный выбор с учётом потенциальной
чувствительности local-part к регистру; поддержка EAI/Unicode и правил отдельных
провайдеров потребует отдельного решения. ASCII punycode-домены допустимы.
Не использовать эту нормализацию как защиту бесплатных генераций от мультиаккаунтов.

## Транзакции и сбои

Записи выполняются через независимые краткоживущие соединения и `BEGIN IMMEDIATE`.
Проверка MAX, поиск существующей связи и создание аккаунта с идентичностью входят
в одну транзакцию. Конкурентные вызовы для одного MAX ID возвращают один аккаунт.
Уникальность обеспечивается также самой БД. Внешних сетевых операций в транзакциях нет.
Ошибка/конфликт/отмена откатывает всю операцию, включая только что созданный аккаунт.
Существующая идентичность повторно добавляется тому же владельцу идемпотентно;
другому владельцу — конфликт без переноса и без автоматического объединения.

Таймаут ожидания SQLite настраивается (по умолчанию 5 секунд, максимум 30).
`SQLITE_BUSY`/`SQLITE_LOCKED` дают контролируемый `AccountStoreBusy`, без бесконечных
повторов. После ошибки вызывающий сервис может ограниченно повторить **всю** операцию.
Режим журналирования не меняется. Общий глобальный connection не используется.

## Явная миграция v1

Текущий legacy-механизм выполняет множество изменений из `database.init_db()`.
Для изолированного этапа он не подходит: его вызов затронул бы посторонние таблицы.
Поэтому используется минимальный независимый версионируемый механизм.

Миграция создаёт только три новые таблицы и три именованных индекса. DDL и запись
версии выполняются в одной транзакции, без `executescript` с неявным коммитом.
Повторное применение проверяет версию, контрольную сумму, DDL, индексы и FK и ничего
не меняет. Частично созданные таблицы, view вместо таблицы, изменённая контрольная
сумма, неизвестная версия, дополнительные ограничения/триггеры или несовместимые
определения останавливают операцию. Неуправляемая эквивалентная схема автоматически
не присваивается: требуется отдельная проверка. Уже опубликованный DDL v1 нельзя
редактировать — дальнейшие изменения должны стать новой миграцией.

Команды ниже — порядок будущего применения администратором, **не разрешение
применять к production сейчас**. Сначала согласованная резервная копия, проверка
временной синтетической БД и согласованный момент применения. Production backup
не переносить в GitHub или среду разработки.

```bash
# Только read-only проверка явно указанного существующего файла:
venv/bin/python -m accounts.migrate --database /path/to/approved.sqlite3

# Изменение только после отдельного разрешения администратора:
venv/bin/python -m accounts.migrate --database /path/to/approved.sqlite3 --apply
```

Без `--apply` схема только читается. Никаких значений по умолчанию для пути, загрузки
`.env`, запуска бота, изменения `journal_mode` или AI/платёжных запросов нет.
Программно: `await accounts.migrations.migrate(path)`; возвращается `True` при первом
применении и `False` при проверенном повторе. Сообщения CLI намеренно не содержат
личных данных или содержимого SQLite-исключений.

## Следующие этапы и отключение

Будущая привязка MAX должна связать подтверждённую веб-сессию и подтверждённую
личность MAX, иметь одноразовый challenge, TTL, лимиты и двухстороннее согласие.
Если обе личности уже принадлежат разным аккаунтам, текущий слой возвращает
конфликт. Процедуры объединения и переноса оплаченных прав пока **нет**.

При будущем переносе прав необходимо учитывать происхождение каждого пакета,
уникальный ключ переноса и остатки по типам услуг. Нельзя складывать разные виды
кредитов или начислять старые покупки дважды. Этот этап не меняет бесплатные попытки,
тарифы, оплаченные пакеты и существующие заказы.

Отключение: не подключать/отключить вызывающий адаптер; таблицы и данные оставить.
Пока адаптеров вообще нет, обычный MAX-путь неизменен. Не удалять новые таблицы после
появления данных и не восстанавливать старую БД поверх новых пользовательских операций.
Следующий этап — доверенное подтверждение email и сессии, а не перенос балансов.
