# Email-авторизация — этап 1.2А

Внутренний серверный сервис без HTTP, MAX, FSM, `.env` и реального почтового
провайдера. Импорт не открывает БД, не мигрирует схему и не отправляет запросов.
Нет изменений production, платежей, кредитов, тарифов и генераторов. Зависимости —
стандартная библиотека Python и существующий aiosqlite.

## Регистрация и повторный вход

`AuthService(path, settings, sender)` требует явные БД, настройки и почтовый адаптер.
`request_email_code(email, source=...)` использует `accounts.models.normalize_email`.
Ни аккаунт, ни legacy users до проверки кода не создаются. Ответ одинаков для
зарегистрированного и нового email; факт регистрации не проверяется при запросе письма.
Ответ не содержит код или признак существования аккаунта. Ошибка синтаксиса email
и ограничение частоты не сообщают ничего о регистрации адреса.

Криптографически случайный код (`secrets.randbelow`) связывается HMAC-SHA256 с
назначением, challenge UUID и нормализованным адресом. В БД — только MAC кода.
`verify_email_code(challenge_id, code, source=...)` сравнивает MAC через
`hmac.compare_digest`. После проверки внутри одной write-транзакции создаётся
`VerifiedIdentity`, извлекается существующий или создаётся новый аккаунт через
внутреннее расширение AccountRepository, создаётся сессия и погашается challenge.
Клиент не передаёт account_id, VerifiedIdentity или выбранный им session token.
Новый аккаунт никогда не получает фиктивный MAX ID, кредит или бесплатную попытку.

## Настройки

`AuthSettings` передаётся явно; автоматического чтения окружения нет.

| Поле | По умолчанию |
| --- | --- |
| secret | Обязательные отдельные секретные bytes, минимум 32 байта |
| environment | production |
| service_name | Bot-Max |
| code_digits | 6 (допустимо 6–8) |
| code_ttl | 600 секунд |
| resend_interval | 60 секунд |
| challenge_attempts | 5 |
| rate_window | 3600 секунд, скользящее окно |
| email_requests / source_requests / global_requests | 5 / 30 / 1000 |
| email_attempts / source_attempts / global_attempts | 20 / 100 / 5000 |
| delivery_timeout | 10 секунд, максимум 60 |
| session_lifetime | 30 дней |
| session_idle | 7 дней |
| session_touch | 300 секунд |
| retention | 1 день после истечения / отзыва |

Запрещено использовать MAX_BOT_TOKEN или ключ AI в качестве auth secret. Будущий
entrypoint должен загрузить отдельный секрет из предназначенного для него хранилища,
не показывать его в логах и не передавать через публичные API. Для разных процессов
нужны одинаковые настройки и секрет. Ротация секрета аннулирует старые MAC кодов и
меняет ключи rate-limit; её нужно планировать, а не выполнять незаметно при рестарте.
Сессии на случайных токенах не отзываются автоматически от ротации auth secret.

## Постоянные лимиты

`auth_rate_limits` хранит события запросов/попыток: ID, тип, хешированный ключ и UTC
Unix timestamp. Email/source-ключи защищены HMAC с отдельными контекстами. Сырые IP,
User-Agent и произвольные заголовки не сохраняются. Для лимита глобального объёма
используется общий ключ. Это небольшой журнал скользящего окна, а не словарь памяти.
Чтение квот и добавление событий сериализованы `BEGIN IMMEDIATE`.

Неверные попытки коммитятся, даже когда наружу возвращается InvalidCode. Общий
email-бюджет не сбрасывается новым challenge или сервисом. Неизвестные challenges
тоже расходуют source/global-бюджеты. Ошибки БД/отмена транзакции откатывают события
вместе с остальными данными. Повторная отправка считается новым запросом, соблюдает
cooldown и квоты; предыдущий challenge аннулируется. Автоповтора отправки нет.
Верхние размеры ввода ограничены; неправильный формат короткого кода считается
ошибочной попыткой, а не способом обойти счётчик.

`source` — ключ, вычисленный будущим доверенным серверным транспортом. Это не поле,
которому можно доверять из тела браузерного запроса. Текущий внутренний сервис не
определяет сам IP клиента. Email, даже подтверждённый, не доказывает уникальность
физического лица; эти лимиты не заменяют защиту бесплатных генераций от мультиаккаунтов.

## Почтовый адаптер и доставка

Порт `EmailSender.send(LoginEmail)` и контракт будущего `SMTPTransport` не содержат
реального подключения. `FakeEmailSender` держит письма в памяти только для тестов;
AuthService запрещает его вне `environment='test'`. Такой режим нельзя выбирать по
пользовательскому запросу. Реальной production-почты в этом этапе нет.

Шаблон:

> Код для входа
>
> [Название сервиса]
>
> Ваш код для входа: XXXXXX.
>
> Код действителен 10 минут.
>
> Если вы не запрашивали код, проигнорируйте это письмо.
>
> Никогда не передавайте код другим людям.

Отправка выполняется вне write-транзакции с ограниченным ожиданием.
`pending` сохраняется до вызова адаптера, `sent` означает подтверждение приёма,
`failed` — доказанную неотправку (`DeliveryFailed`), `unknown` — таймаут/неизвестный
исход. Исключения доставки с потенциальными секретами не логируются и не возвращаются.
Успешная передача адаптеру не доказывает доставку во входящие.

Ответ запроса остаётся одинаковым при ошибке адаптера. Для `failed` код не действует;
при `unknown` он может быть принят, если письмо всё-таки пришло и соблюдены все
остальные ограничения. Зависший `pending` после истечения delivery_timeout при
проверке переводится в `unknown`: платного/повторного письма не отправляется.
Отмена операции во время отправки также оставляет неопределённый исход. TTL считается
от создания challenge и не продлевается задержкой доставки. Повторный запрос после
cooldown создаёт новый код, аннулируя старый, даже если старая доставка запоздала.

## Сессии

`secrets.token_urlsafe(32)` даёт 256 бит случайности; новый токен создаётся только
сервером при каждой успешной проверке. В БД хранится SHA256 случайного токена,
а не сам токен. Это допустимо для высокоэнтропийного секрета, в отличие от короткого
OTP, где нужен HMAC. Хеш или session_id нельзя использовать вместо bearer-токена.
`LoginResult.token` отдаётся доверенному транспорту один раз и скрыт из repr.

`auth_sessions`: session_id, account_id FK, уникальный token_hash, created_at,
last_seen_at, expires_at, idle_expires_at, revoked_at. Даты — UTC Unix seconds.
`get_current_account(token)` проверяет отзыв, абсолютный и idle TTL. Обновление
активности ограничено session_touch; обычное чтение использует read-only соединение.
Idle-граница отсчитывается от последнего сохранённого касания: возможна погрешность
в сторону более раннего завершения до session_touch, но не восстановление истёкшей
сессии. Абсолютный TTL никогда не продлевается.

`logout(token)` идемпотентно отзывает одну сессию. `logout_all(token)` требует
действующую сессию и выводит account_id из неё; аккаунт из пользовательского ввода
не принимается. Несколько устройств имеют разные токены. Проверка и отзыв
линеаризуются транзакциями; запрос, проверивший сессию до конкурентного отзыва,
может завершить уже начатую проверку. Следующая проверка отозванный токен отвергает.
Будущие чувствительные операции должны повторно проверять права в своей транзакции.

Если ответ успешного подтверждения потерян после коммита, повторное использование
кода запрещено: открытый session token из хеша не восстанавливается. Нужно новое
подтверждение после cooldown; лишняя сессия затем истечёт/будет отозвана. После
доказанного отката транзакции тот же ещё действующий код можно проверить повторно.

## Транзакции и миграции

В auth нет вложенных независимых write-транзакций. Внутренний метод
`AccountRepository._get_or_create_verified_email_in_transaction(db, proof)` работает
в переданном соединении, без коммита/отдельного connection. Вызывается только
доверенным сервисом после проверки OTP. Конкурентные операции сериализуются,
уникальность account_identities дополнительно защищена индексом этапа 1.1.
При сбое/отмене откатываются новый аккаунт, идентичность, сессия и погашение кода.
SQLite busy/locked возвращает контролируемую ошибку без бесконечных повторов.

Исходный DDL v1 и CHECKSUM **не изменены**. Общий runner теперь знает последовательность
v1 → v2. v2 добавляет auth_challenges, auth_sessions, auth_rate_limits и индексы.
Версии должны идти без пропусков с исходными именами/контрольными суммами; неизвестные
версии, частичные или несовместимые таблицы останавливают миграцию. Новая база получает
обе версии в одной транзакции; база v1 — только v2. Повтор — проверка без изменения.
Legacy-таблицы, режим журналирования и запуск бота не меняются. Автоматических
миграций нет. `migrate(path,target=1)` оставлен для тестирования совместимости v1;
понижение существующей базы v2 запрещено.

CLI по умолчанию только читает; применение текущей последовательности — отдельно
после разрешения администратора и резервного копирования:

```bash
venv/bin/python -m accounts.migrate --database /path/to/approved.sqlite3
venv/bin/python -m accounts.migrate --database /path/to/approved.sqlite3 --apply
```

Эти команды на production в рамках этапа не выполнялись. Применение не запускает
сервис. `cleanup_expired()` удаляет просроченные challenges после retention,
старые события лимитов после полного окна и завершённые сессии. Его будущий
планировщик должен запускать явно; сейчас фонового процесса очистки нет.

## Будущий HTTP-слой — пока НЕ реализован

- HttpOnly/Secure cookie с SameSite=Lax или более строгим совместимым значением.
- Ограниченный Path и host-only cookie; token не в localStorage и не в URL.
- Origin-проверка, CSRF-защита изменяющих запросов, ограниченный CORS без wildcard
  с credentials, ограничения размеров тела и частоты на reverse proxy.
- Не доверять произвольному X-Forwarded-For: разбирать его только от явно доверенного
  Nginx/proxy и нормализовать серверный source key.
- Не возвращать модели БД, traceback, email других аккаунтов, MAC и хеши токенов.
- Не принимать VerifiedIdentity от клиента и не превращать внутренние методы в API.
- После смены email, привязки MAX и других чувствительных действий — пересмотр/отзыв сессий.
- Отдельная двухсторонняя привязка MAX с одноразовым challenge и доказательством
  владения обоими аккаунтами. Здесь она не реализована, балансы не объединяются.

Также отсутствуют SMTP-подключение, веб-интерфейс и общий процесс подтверждения
принадлежности физическому лицу. Этот этап не предназначен для включения публичной
авторизации до реализации и проверки транспорта, почты и браузерных защит.

## Дополнительные границы модели угроз

Часы берутся на сервере; после ожидания write-lock время повторно считывается
внутри транзакции. Сессия/код, истёкшие за время ожидания SQLite, не оживают.
Нужны согласованные системные часы процессов; клиентские timestamps не принимаются.
Кража открытого bearer-токена даёт доступ до отзыва/истечения: защита браузера,
TLS и безопасные cookie обязательны на следующем этапе. Компрометация почтового
ящика позволяет войти по email; этот этап не добавляет второй фактор. Раздельное
хранение серверного секрета защищает короткие коды от офлайн-перебора при утечке
только БД, но не от компрометации самого сервера вместе с секретом.

Будущий почтовый адаптер должен уважать отмену и иметь собственные сетевые таймауты:
`asyncio.wait_for` не может принудительно остановить блокирующий или подавляющий
отмену код. Текущий Fake-адаптер и тестовые сценарии соблюдают этот контракт.
